# ADR-024 — Agent Returns Data; Backend Owns All DB Writes

## Status
Accepted

## Date
2026-05-16

## Context

The agent service parses a financial statement and produces `ParsedTransaction[]`.
Those rows need to reach the database as `needs_review` records.

Two approaches were considered for how parsed data moves from agent to DB:

**Option A — Agent calls backend to persist (callback pattern)**
```
backend → POST /parse → agent parses → agent POST /ingestion/store → backend writes DB
                                                                    ← 200
                        agent returns 200 to original backend call ←
backend returns to frontend ←
```

**Option B — Agent returns data; backend persists (return pattern)**
```
backend → POST /parse → agent parses → returns ParsedTransaction[]
backend writes DB ←
backend returns to frontend ←
```

## Decision

**Option B — agent returns data; backend persists.**

The agent is a pure parsing service. It has no DB credentials, no schema knowledge,
and no concept of `investment_transaction` vs `expense` tables. The backend already
holds the open HTTP request; it receives the parsed rows and performs the INSERT in
its own transaction, using its own DB pool.

## Why Not Option A

Option A creates a circular in-flight request: the backend is waiting on the agent
(open HTTP connection), and the agent calls back into the backend on a different endpoint.
This is architecturally awkward and creates several problems:

- **Partial failure ambiguity**: if the agent's callback to `/ingestion/store` fails,
  the agent has already "finished" from its own perspective. The backend's open request
  gets a success from the agent but the rows were never written. The frontend sees
  success but nothing was stored.
- **Two network hops instead of one**: agent → backend (callback) + return to original
  caller = two round trips where one suffices.
- **Coupling grows**: the agent needs to know the backend's internal endpoint, its
  authentication, and the exact shape of the ingestion API. Changing the backend's
  ingestion endpoint requires a coordinated agent update.
- **Testability degrades**: testing the agent requires standing up a backend (or a mock)
  to receive the callback — the agent cannot be tested in isolation.

## Consequences

**Good:**
- Agent is stateless and has no DB dependencies — testable in isolation with fixture files
- Single point of DB write: the backend's `IngestionService` controls the INSERT,
  wrapping it in a transaction if needed
- No circular in-flight calls; failure modes are straightforward:
  - Agent parse fails → backend receives error → frontend sees error, nothing written
  - Agent parse succeeds → backend INSERT fails → frontend sees error, agent is unaffected
- Backend can enrich the rows before writing (e.g. attach `personId`, set `status`)
  without the agent knowing about the DB schema

**Accepted trade-offs:**
- The agent response payload can be large for statements with 200+ transactions;
  acceptable for a sync flow on a local network (backend → agent is loopback)
- The backend must handle the full `ParsedTransaction[]` in memory before writing —
  not streamed; acceptable at current scale
