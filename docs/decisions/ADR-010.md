# ADR-010: Immutable Ledger Pattern for Investment Transactions

## Status
Accepted

## Date
2026-04-24

## Context
The original `investment` table modelled each holding as a single row with sell columns
(`sold_date`, `sold_quantity`, `sold_at_price`, `realised_value`). This broke down under
partial sells — there was no clean place to record selling 50 of 100 units without either
overwriting the original row or creating ambiguous duplicates. XIRR computation was also
impossible because it requires a series of dated cash flows, not a single net row.

## Decision
Replace the `investment` table with two tables:

**`investment_transaction`** — immutable ledger. Every BUY and SELL is always a new row.
Never updated or deleted. This is the single source of truth for XIRR and realised P&L.
Key columns: `asset_id`, `person_id`, `financial_institution_id`, `type` (buy/sell/dividend),
`quantity`, `price`, `amount`, `transacted_at`, `status`, `is_seed`, `source`.

**`holding`** — derived state. One row per asset, household-wide (no `person_id`).
Stores current quantity, weighted average cost, total invested, and current price/value.
Recomputed synchronously from `investment_transaction WHERE status = 'confirmed'` after
every transaction confirmation. Never used as a ledger — if data looks wrong, delete all
rows and recompute from transactions.

### Partial sell handling
```
BUY  100 units @ ₹150 → transaction row; holding: qty=100, avg_cost=150
SELL  50 units @ ₹200 → transaction row; holding: qty=50,  avg_cost=150 (unchanged)
```
Average cost does not change on sell. Realised P&L = (sell_price − avg_cost) × qty_sold,
computed on read by summing over SELL transaction rows.

### XIRR cash flows
```
Every BUY  → negative flow (−amount, transacted_at)
Every SELL → positive flow (+amount, transacted_at)
Terminal   → positive flow (+current_value, today)
```

### Holding recompute logic
```sql
SELECT type, quantity, price
FROM investment_transaction
WHERE asset_id = $1 AND status = 'confirmed'
ORDER BY transacted_at ASC
```
Iterate: BUY → totalCost += qty × price, qty += qty.
         SELL → totalCost -= qty_sold × (totalCost / qty), qty -= qty_sold.
avg_cost = totalCost / qty (if qty > 0).

## Alternatives Considered

### Keep `investment` with sell columns
Rejected: Cannot handle partial sells. Cannot compute XIRR without dated cash flows.
Ambiguous state when multiple partial sells occur on the same holding.

### Lot-based model (one row per buy lot, sell references a lot)
Considered: More precise FIFO/LIFO tracking. Rejected for Phase 2 as unnecessary
complexity — the average cost method is the standard Indian tax/reporting method and
sufficient for all planned features.

## Consequences
- XIRR is now computable from real dated cash flows
- Partial sells work correctly
- `holding` table is fully recoverable from `investment_transaction` at any time
- `investment_statement_id` is nullable to support manual and seeded transactions
- All portfolio reports query `investment_transaction WHERE status = 'confirmed'` for
  XIRR inputs and `holding` for current value and allocation
- Supersedes the `investment` table defined in ADR-004 / `001_init.sql`
