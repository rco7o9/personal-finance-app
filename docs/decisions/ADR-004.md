# ADR-004: Staging via Status Enum on Main Tables, Not Separate Staging Tables

## Status
Accepted

## Date
2026-04-19

## Context
The AI-assisted ingestion flow (Phase 3) parses uploaded PDF/CSV statements and
creates expense and investment rows that need human review before being treated
as confirmed data. These "pending" rows must be stored somewhere while awaiting
review, kept out of reports, and transitioned to confirmed (or excluded) after
the HITL review step.

The question was where unreviewed rows should live during the review window.

## Decision
No separate staging tables. Pending rows live directly in the `expense` and
`investment` tables alongside confirmed data, differentiated by a `status`
column using a PostgreSQL enum.

The enum values are: `pending`, `confirmed`, `edited`, `excluded`.

- Ingestion writes rows with `status = 'pending'`.
- The HITL review UI queries `WHERE status = 'pending'` to show the inbox.
- On user approval, the row transitions to `status = 'confirmed'` (or `'edited'`
  if the user modified values before confirming).
- Rows the user rejects become `status = 'excluded'`.
- All reporting queries filter `WHERE status = 'confirmed'`. This is a hard rule.

## Alternatives Considered

### Separate expense_staging / investment_staging tables
- Pros: Clean physical separation between reviewed and unreviewed data. Reports
  query only the main table with no status filter needed. Clear blast radius if
  staging data is deleted.
- Cons: Duplicates the full table schema — any column addition requires a
  migration on both tables. Moving a row from staging to main requires an
  INSERT + DELETE (or stored procedure), not a simple UPDATE. Foreign key
  relationships (e.g. to categories, platforms) must be maintained in both
  tables. Schema drift between staging and main tables is a real maintenance risk
  over time.
- Rejected: Schema duplication and the INSERT/DELETE promotion pattern add
  complexity without meaningful benefit for a single-user review flow.

### Soft-delete pattern (deleted_at timestamp)
- Pros: Common pattern, easy to implement, allows recovery of "deleted" rows.
- Cons: Solves a different problem (logical deletion and recovery) rather than
  pre-review staging. A `deleted_at` column has no natural mapping to the
  `pending → confirmed` state machine.
- Rejected: Wrong tool for this problem.

### Event sourcing (append-only event log)
- Pros: Full audit trail of every state transition. Replay-able history.
- Cons: Massive complexity increase — requires an event store, projections, and
  a read model. Entirely disproportionate for a personal finance app.
- Rejected: Not appropriate for this scale and use case.

## Consequences
- Every reporting query MUST include `WHERE status = 'confirmed'`. Omitting this
  filter is a silent correctness bug that inflates reported figures with pending
  data. This must be enforced in code review.
- The `status` enum provides a lightweight audit trail: we can see which rows
  were edited before confirming, which were excluded, and how many are still
  pending.
- Schema changes to `expense` or `investment` apply once and immediately affect
  both pending and confirmed rows — no dual-migration required.
- The HITL review inbox is a simple query: `WHERE status = 'pending' ORDER BY
  created_at`.
- `excluded` rows are retained in the table (not deleted), which allows
  reviewing what was excluded and why.
