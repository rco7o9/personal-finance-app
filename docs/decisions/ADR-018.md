# ADR-018 — Native-Currency Columns on `holding`

## Status
Accepted

## Date
2026-04-25

## Context

The `holding` table stores all monetary values (`avg_cost`, `total_invested`,
`current_price`, `current_value`) exclusively in INR. For US equity holdings,
this means:

- `avg_cost` is in INR (correct per ADR-017, computed from `amount_inr`)
- `current_price` is in INR (AssetPriceService always returns INR)
- But the asset was purchased in USD, so there is no way to display
  USD-denominated cost or price in the UI

The user wanted to see `"$123.45 / ₹10,300"` for avg cost and
`"$150.00 / ₹12,500"` for current price on US equity detail pages,
alongside INR values. The lot table also needed native-currency Cost and
Current Value columns.

Two options were considered:

**Option A — Store native-currency values as columns on `holding`**
- Add `native_currency VARCHAR(3)`, `native_avg_cost NUMERIC(18,4)`,
  `native_total_invested NUMERIC(18,4)`, `current_price_native NUMERIC(18,4)`,
  `current_value_native NUMERIC(18,4)` as nullable columns
- `native_avg_cost` / `native_total_invested` backfilled by a seed script from
  `investment_transaction.amount` (the original native-currency amount)
- `current_price_native` / `current_value_native` populated during price refresh

**Option B — Compute on the fly from INR price + live rate**
- No schema change
- Divide `current_price` (INR) by the live USD/INR rate from `CurrencyService`
  to derive the USD price at read time
- `native_avg_cost` would need a similar back-calculation

## Decision

**Option A was chosen.**

Five new nullable columns added to `holding` via migration 006:

```sql
ALTER TABLE holding
  ADD COLUMN native_currency        VARCHAR(3),
  ADD COLUMN native_avg_cost        NUMERIC(18,4),
  ADD COLUMN native_total_invested  NUMERIC(18,4),
  ADD COLUMN current_price_native   NUMERIC(18,4),
  ADD COLUMN current_value_native   NUMERIC(18,4);
```

INR-denominated assets always have NULL in all five columns. Only USD assets
are populated.

### Why Option A over Option B

**For avg_cost / total_invested**: Option B would compute
`native_avg_cost = avg_cost / current_rate`. This is incorrect — the rate
today is different from the blended rate at which the position was accumulated.
Using `investment_transaction.amount` (the original USD transaction amount) is
the only accurate source. This cannot be derived from `avg_cost` alone.

**For current_price**: Option B would produce a price that changes every time
the USD/INR rate moves, even when no market price fetch has occurred. The
stored `current_price_native` is the exact price returned by Finnhub at refresh
time — consistent with the stored `current_price`.

**Consistency with ADR-017**: `amount_inr` is stored on the ledger rather than
computed, for the same reasons. Storing derived-but-accurate values is the
established pattern.

### Why NULL for INR assets (not redundant INR copies)

Storing `native_avg_cost = avg_cost` for an INR asset would double the data
without adding value. The frontend checks `nativeCurrency !== null` to decide
whether to render the dual-currency format. NULL = INR-only display, non-null =
dual-currency display.

### Why `native_avg_cost` uses `investment_transaction.amount`, not a rate calculation

`investment_transaction.amount` is the exact USD amount paid at transaction
time, as recorded by the broker. Dividing `avg_cost` (INR, blended across
multiple transactions at different rates) by any single rate would produce a
number that does not correspond to any actual transaction amount.

### Seed script

`backend/scripts/seed-native-columns.ts` — idempotent, safe to re-run:
1. Aggregates net USD quantity and net USD amount per asset from
   `investment_transaction` (using the native `amount` column, not `amount_inr`)
2. UPDATEs USD holdings with `native_currency = 'USD'`, `native_avg_cost`,
   `native_total_invested`
3. NULL-resets all native columns for INR assets (idempotent)

```
npm run seed:native-columns  # cd backend first
```

### Price refresh

`AssetPriceService.batchFetchFinnhubWithNative()` is a new method that returns
`{ priceUsd: Decimal, priceInr: Decimal }` per US equity asset. The existing
`batchFetchFinnhub` and `batchFetchYahooFinancePrices` are unchanged.

`refreshHoldingPrices()` now splits `yahoo_finance` assets into Indian
(`.NS`/`.BO`) and US (no suffix). Indian assets continue to use the existing
batch path; US assets use `batchFetchFinnhubWithNative` and receive a richer
DB UPDATE that includes native price columns.

## Consequences

**Good:**
- UI can show `"$123.45 / ₹10,300"` for avg cost and current price on US
  equity detail pages
- Lot table shows native cost and current value per transaction
- No rate-division arithmetic on the read path — stored values are exact
- Consistent with the ADR-017 pattern (store accurate derived values close
  to source of truth)

**Bad / Accepted:**
- Five extra nullable columns on `holding` (negligible storage for a personal
  app)
- `seed-native-columns.ts` must be re-run if new USD transactions are added
  (same caveat as `seed-amount-inr.ts`)
- `current_price_native` is only as fresh as the last price refresh — same
  caveat as `current_price`
