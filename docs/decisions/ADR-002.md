# ADR-002: No ORM — Raw SQL via node-postgres with pgtyped for Type Safety

## Status
Accepted

## Date
2026-04-19

## Context
The backend needs to query PostgreSQL. The two competing concerns were: (1) full
control over the exact SQL being executed — important for financial queries where
precision and auditability matter — and (2) TypeScript type safety on query
results, without writing manual type annotations for every row shape.

The app uses PostgreSQL-specific types (`NUMERIC(18,4)`, custom enums, `DATE` for
month columns) that require careful handling. Any abstraction that generates SQL
automatically risks obscuring or mishandling these types.

## Decision
Raw SQL via `node-postgres` (`pg`). No ORM.

- Migrations are plain numbered `.sql` files in `backend/migrations/`, run by a
  custom migrate script.
- All reusable queries live in `.sql` files under `backend/queries/`.
- `pgtyped` reads those `.sql` files and generates TypeScript types automatically,
  giving compile-time safety on query inputs and outputs without a query-builder DSL.
- All `pool.query()` calls pass the row type generic: `pool.query<MyRowType>(sql, params)`.

## Alternatives Considered

### Prisma
- Pros: Excellent DX, auto-generated migrations, type-safe client, large ecosystem,
  great documentation.
- Cons: Prisma generates SQL on your behalf — you don't always know what query it
  will produce. For financial data this is a liability. Prisma's migration system
  (`prisma migrate dev`) has footguns with complex schemas and custom types. Its
  generated client adds bundle overhead and a compile step (`prisma generate`).
  `NUMERIC` columns are returned as strings in Prisma too, so the type-safety
  benefit over pgtyped is marginal.
- Rejected: Loss of SQL visibility is unacceptable for financial queries. We want
  to read every query that hits the DB.

### Drizzle ORM
- Pros: Lightweight, SQL-like TypeScript DSL, no code generation step, schema
  defined in TypeScript.
- Cons: Still an abstraction over SQL — the DSL is not SQL, and complex queries
  (window functions, CTEs for XIRR) become awkward to express. Schema defined in
  TypeScript means schema and migrations are decoupled in a non-obvious way.
- Rejected: For complex financial aggregations we'll inevitably write raw SQL
  anyway; better to commit to it consistently from the start.

### Kysely
- Pros: SQL-like query builder with strong TypeScript types, no magic generation.
- Cons: Kysely's types come from a manually-maintained schema type you define in
  TypeScript — more maintenance than pgtyped, which derives types directly from
  the `.sql` files. Another DSL to learn.
- Rejected: pgtyped gives equivalent type safety with less manual upkeep because
  types are derived from the actual SQL, not a parallel TypeScript definition.

### TypeORM
- Pros: Mature, decorator-based, familiar to Java/Spring developers.
- Cons: Known for generating inefficient SQL. Decorator-heavy style conflicts with
  our preference for explicit code. Migration system is fragile.
- Rejected early. Not seriously considered.

## Consequences
- `npm run codegen` must be run after any change to `backend/queries/*.sql` to
  regenerate types. The database must be running when codegen runs (pgtyped
  connects to introspect the schema).
- Migrations are reviewable plain SQL — easy to audit, easy to reason about,
  easy to roll back manually if needed.
- No magic: every query the app executes is readable in the source tree.
- `node-postgres` returns `NUMERIC` columns as JavaScript strings by default.
  Any arithmetic on money/quantity values in TypeScript must use a decimal
  library (e.g. `decimal.js`) — never native JS `number`.
- Slightly more boilerplate per query compared to an ORM (explicit SQL + type
  annotation), but this is a deliberate trade-off for visibility and control.
