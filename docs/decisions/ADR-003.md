# ADR-003: No Authentication — personId via localStorage and URL Parameter

## Status
Accepted

## Date
2026-04-19

## Context
The app tracks finances for exactly two people: Arjun and Priya. It runs
locally via Docker Compose and is not exposed to the internet. The primary
need is per-person data attribution (whose expense is this? whose investment?)
— not access control. Adding a full auth system would introduce login screens,
session management, and token infrastructure for a threat model that doesn't
exist in local-only deployment.

## Decision
No authentication. Person selection is a UI convenience, not a security gate.

- A `PersonSelector` dropdown in the TopBar (client component) lets the user
  indicate who they are.
- The selected `personId` is persisted in `localStorage`.
- It is also synced into the URL as `?personId=X` so server components can
  read it (server components cannot access `localStorage`).
- Server components that need `personId` read it from the `searchParams` prop.
- The NestJS backend does not validate or enforce personId — it trusts what
  the frontend sends.

## Alternatives Considered

### NextAuth / Auth.js
- Pros: Battle-tested, supports OAuth providers (Google, GitHub), session
  management via JWT or DB sessions, good Next.js integration.
- Cons: Requires configuring an OAuth provider or credential store, adds
  `sessions` table to the DB, introduces callback URLs and environment
  variables. Complete overkill for a two-person local app with no threat model.
- Rejected: The complexity-to-benefit ratio is unjustifiable for this use case.

### Clerk
- Pros: SaaS auth with excellent DX, pre-built UI components, handles MFA.
- Cons: External SaaS dependency, requires internet connectivity, paid beyond
  free tier. Creates a hard dependency on a third-party service for a local app.
- Rejected: External dependency on an auth SaaS for a private local tool is
  an unnecessary risk and cost.

### Supabase Auth
- Pros: Integrated with Postgres, row-level security, open source self-hostable.
- Cons: We're already self-hosting Postgres directly via Docker — adding Supabase
  Auth would require either the full Supabase stack or a partial integration.
  Overengineered for the use case.
- Rejected: Conflicts with our direct-Postgres approach.

### HTTP Basic Auth at the Docker/nginx level
- Pros: Zero application code, gates the entire app with a username/password.
- Cons: Doesn't solve per-person attribution (knowing it's "Arjun" vs "Priya"
  for expense splitting). A single shared password doesn't distinguish users.
  Would require an nginx reverse proxy not currently in the stack.
- Rejected: Solves access control (which we don't need) but not identity (which
  we do need for attribution).

### Simple JWT/cookie auth with a hardcoded user table
- Pros: Standard pattern, no external dependencies, could be built in NestJS.
- Cons: Login screen, token refresh logic, cookie configuration, HTTPS concerns
  for cookies — all complexity serving no real security need for a local app.
- Rejected: Meaningful implementation cost with no security benefit given local
  deployment.

## Consequences
- No security boundary. Anyone with network access to the Docker host can view
  and modify all data. Acceptable while the app is local-only; must be
  revisited before any internet-facing deployment.
- Every server component that needs `personId` must accept `searchParams` as a
  prop and forward it through the component tree — this is a recurring pattern.
- Links between pages must preserve `?personId=X` in the URL, or the server
  component will lose context.
- The NestJS backend receives `personId` as a request parameter and uses it for
  data filtering, but performs no authentication check on it.
