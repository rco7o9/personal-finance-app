# ADR-007: Portfolio Values Computed at Runtime via Live Price Fetching — No Price Snapshot Table

## Status
Accepted

## Date
2026-04-20

## Context
The Portfolio Overview screen (Phase 2) needs current portfolio value, unrealised
gains, and XIRR for each asset and the portfolio as a whole. This requires a
current market price for each held asset. The question is whether to store periodic
price snapshots in the database or fetch prices live at request time.

## Decision
No price snapshot table in the schema. Portfolio values are computed at runtime:
the backend fetches the current price for each asset from the appropriate market
API at request time, multiplies by held quantity, and returns the computed values
directly in the API response.

Each `asset` row carries `ticker_symbol`, `exchange`, and `price_source`
(`yahoo_finance`, `amfi`, `coinmarketcap`, `manual`) so the backend knows which
API to call per asset type.

In Phase 2, a daily background job will update a cached/computed value to avoid
hitting external APIs on every page load — but this is an implementation detail,
not a schema requirement.

## Alternatives Considered

### Price snapshot table (periodic polling)
- Pros: Portfolio value is always fast to read (no external API call on page load).
  Historical price data available for charting. No external API dependency at
  read time.
- Cons: Requires a background job and scheduler from day one. Schema complexity
  grows (snapshot table with timestamp + asset + price). Stale data if the job
  hasn't run recently. More moving parts to bootstrap.
- Rejected: Premature complexity for Phase 2. Can be added in Phase 6
  (intelligence layer) if needed for historical charting.

### Store current value on each investment row
- Pros: Simplest reads — no join to a separate price table.
- Cons: Values become stale immediately after write. Requires a sweep update
  job that touches every open investment row whenever prices change. Mixes
  immutable transaction data (buy price, quantity) with mutable market data
  (current value).
- Rejected: Conflates two concerns — the immutable buy record and the live
  market valuation. Wrong separation of concerns.

## Consequences
- Portfolio page load triggers external API calls. Acceptable for a personal
  app with low traffic and a small number of distinct assets.
- The `price_source` and `ticker_symbol` columns on `asset` are the hook
  for the Phase 2 price-fetching service — each asset type routes to a
  different API (Yahoo Finance for US/Indian equities, AMFI for mutual fund
  NAVs, CoinMarketCap/CoinGecko for crypto).
- XIRR computation is also at runtime: buy cashflows come from `investment`
  rows, terminal value = quantity × current price. This is a CPU-bound
  calculation but negligible for a personal app (< 100 holdings).
- If response latency becomes a problem, a Redis/in-memory cache keyed on
  (asset_id, date) can be added in front of the API calls without any schema
  change.
