# ADR-009: In-Memory Price Cache Strategy

## Status
Accepted

## Date
2026-04-24

## Context
The portfolio summary endpoint fetches a live price for every distinct asset in the
portfolio. With 60 assets across five APIs (Finnhub, mfapi.in, CoinGecko, Metals-API,
Frankfurter), fetching all prices on every page load would:
- Exhaust Finnhub's 60 req/min free tier on a single portfolio load
- Add 1–5 seconds of serial latency per page load
- Cause unnecessary repeated calls when the same page is refreshed quickly

## Decision
The `AssetPriceService` maintains an in-memory `Map<assetId, { priceInr: Decimal, fetchedAt: Date }>`
with a TTL of **5 minutes**. The `CurrencyService` maintains a separate in-memory cache
for the USD/INR rate with a TTL of **1 hour**.

### Cache key
`assetId` (integer) — one entry per asset row.

### TTL rationale
- **5 min for prices**: Stock markets update tick-by-tick but for a personal portfolio
  tracker, 5-minute granularity is sufficient. mfapi.in updates only ~6 times daily so
  5 min is more than fresh enough. CoinGecko crypto prices change faster but 5 min is
  acceptable for this use case.
- **1 hour for USD/INR**: ECB rates update once daily; 1-hour TTL is conservative and
  safe.

### Cache miss behaviour
On a cache miss, the service fetches synchronously and stores the result before returning.
No background refresh — the first caller after TTL expiry pays the fetch cost.

### Parallel fetching
When the portfolio service needs prices for N assets, it calls `getPriceInr()` for all
assets in parallel via `Promise.all()`. Cache hits return immediately; only misses trigger
network calls.

### Error handling
If a price fetch fails, `getPriceInr()` logs the error and returns `null`. The portfolio
service skips that asset from totals rather than failing the entire request. The failed
asset is not cached — the next request will retry.

## Alternatives Considered

### Redis cache
Pros: survives process restarts, shareable across multiple backend instances.
Cons: adds a new Docker service and dependency. For a personal single-instance app with
low traffic, the in-process Map is simpler and sufficient.
Deferred to a later phase if needed.

### No cache — fetch on every request
Rejected: would hit Finnhub rate limits immediately on a portfolio with 40+ equities.

### Background refresh job
Considered: a scheduled job refreshes all prices every 5 minutes regardless of requests.
Rejected for Phase 2a: adds complexity (scheduler, job state). The on-demand cache with
5-min TTL achieves the same user-visible behaviour.

## Consequences
- In-process cache is lost on process restart — first request after restart fetches all
  prices live (acceptable for a personal app)
- Cache is not shared between multiple backend instances (not relevant — single instance)
- Upgrade path to Redis: replace `Map` in `AssetPriceService` with a Redis client;
  no interface changes required
