# ADR-023 — Gemini source_text Extraction; No PDF Parsing Library

## Status
Accepted

## Date
2026-05-16

## Context

The HITL review screen must show the original statement row alongside the AI-parsed
version so the user can verify accuracy. This requires capturing what the source document
actually said for each extracted transaction.

The obvious approach — extract text from the PDF using a parsing library, then align
rows to parsed transactions — was rejected after evaluating the available options.

**PDF parsing library options evaluated:**
- `pdf-parse` — fails on multi-column layouts, returns garbled text for most financial
  statement PDFs; no support for scanned PDFs
- `pdfjs-dist` — better than pdf-parse but still fragile on table layouts, ligatures,
  and non-standard fonts common in bank statement PDFs
- `pdf2image` + page rendering — shows the visual page, not the specific row; requires
  coordinate mapping to link a parsed transaction to a visual region, which is itself
  an unsolved problem without additional LLM work

The agent already sends the full PDF to Gemini for extraction. Gemini reads the PDF
visually and textually — it can see the exact text of each row it extracts.

## Decision

Add `source_text` as a required field in the Gemini structured output schema.
Instruct Gemini in the system prompt:

> *"For each transaction, populate `source_text` with the exact verbatim text of that
> row as it appears in the statement — preserve spacing, punctuation, and amounts exactly
> as printed. Do not reformat or paraphrase."*

No PDF parsing library is used anywhere in the agents service.

For deterministic CSV/XLSX parsers, `source_text` is the raw joined cell values of
that row — assembled by the parser itself with no LLM involvement.

## Why This Works

Gemini is already reading the PDF to extract structured data. Asking it to also return
the verbatim row text is a zero-cost addition to the same call — no extra API round trip,
no extra model. Because Gemini performs visual + text understanding, it handles scanned
PDFs, non-standard fonts, and complex table layouts that defeat all text-extraction
libraries.

The HITL review UI then shows a simple side-by-side:

```
SOURCE (from PDF)                                │  PARSED
─────────────────────────────────────────────────┼───────────────────────────────
15 Jan 2024   AMAZON.COM*AMZN    1,250.00 Dr     │  Date: Jan 15 · ₹1,250 · Shopping
                                                 │  Confidence: 95%
```

`source_text` is stored in `raw_source JSONB` on the transaction row alongside the
full Gemini output object.

## Alternatives Considered

### pdfjs-dist text extraction + row alignment
Rejected. Financial statement PDFs use table layouts that produce garbled multi-column
text when extracted linearly. Alignment between extracted text rows and parsed
transactions requires heuristic matching that is fragile and untestable.

### pdf2image page rendering
Rejected. Renders a full page image — the user would need to visually scan the page
to find the relevant row. Does not scale for statements with 100+ transactions per page.
Coordinate-level row highlighting would require Gemini bounding-box output, adding
significant complexity.

### Store page number + ask user to cross-reference
Rejected. Forces the user to open the original PDF and find the row manually —
defeats the purpose of the review screen.

## Consequences

**Good:**
- Zero PDF parsing library dependency in `agents/`
- Works for scanned PDFs (Gemini OCR handles them; no library does reliably)
- `source_text` fidelity is as good as Gemini's reading — which is better than any
  text-extraction library for financial statement formats
- Review UX is clean: one field, no page navigation required

**Accepted trade-offs:**
- If Gemini hallucinates `source_text` (paraphrases instead of quoting verbatim), the
  review display is misleading. Mitigation: include explicit verbatim instruction in the
  system prompt; spot-check during manual E2E testing.
- `source_text` adds tokens to the Gemini response — negligible for financial statements
  (each row is ~100 characters).
