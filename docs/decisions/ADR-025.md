# ADR-025 — Static Code-Based Skill Registry; Known Platforms Only

## Status
Accepted

## Date
2026-05-16

## Context

The agent service needs to map an incoming `platform` identifier to a `SkillTemplate` —
a structured knowledge document containing the system prompt template, column mappings,
few-shot examples, and balance check strategy for that platform.

Three approaches were evaluated:

1. **Static code registry** — a `Record<platformId, SkillTemplate>` in `registry.ts`;
   adding a platform requires a code change and redeploy
2. **DB-backed dynamic registry** — skill templates stored in a `platform_skill` table;
   registry queries DB (with in-memory cache); new skills approved via a separate HITL
   flow without a redeploy
3. **Skill-author LLM** — a reasoning model generates a candidate skill template at
   runtime when an unknown platform is encountered; human reviews and the registry
   self-populates

## Decision

**Static code registry. Unknown platform → HTTP 400.**

```typescript
// skills/registry.ts
const REGISTRY: Record<string, SkillTemplate> = {
  "zerodha"     : zerodhaSkill,
  "indmoney"    : indmoneySkill,
  "coinswitch"  : coinswitchSkill,
  "paytm-money" : paytmMoneySkill,
  "employer-stock"    : employerStockSkill,
  "hdfc-bank"   : hdfcBankSkill,
};

export function getSkill(platformId: string): SkillTemplate {
  const skill = REGISTRY[platformId];
  if (!skill) throw new SkillNotFoundError(platformId, Object.keys(REGISTRY));
  return skill;
}
```

The Express handler catches `SkillNotFoundError` and returns 400 with a message listing
supported platforms.

## Why Not DB-Backed Dynamic Registry

A DB-backed registry was fully designed during the architecture session and then
deliberately set aside. The reasons:

- **The platform set is fixed and small** (6 platforms). There is no operational pressure
  to add platforms without a deploy.
- **Skill templates require careful authoring**. A system prompt template for Paytm Money
  PDFs encodes knowledge about the column layout, date format, amount sign conventions,
  and known edge cases. This is not content that should be generated at runtime or
  approved quickly through a UI — it deserves the same review rigour as application code.
- **DB-backed registry adds operational complexity**: a new migration (`platform_skill`
  table), a new backend module (`SkillReviewModule`), cache invalidation between backend
  and agent, a new frontend route for skill review. All of this for a problem that a
  one-line code change solves.
- **The code registry is the ground truth**. Version-controlled skill templates give you
  git history, code review, and rollback — none of which a DB table provides.

## Why Not Skill-Author LLM (Runtime Generation)

The skill-author pattern — using a reasoning model to generate a skill template when
an unknown platform is encountered — was evaluated and rejected:

- Skill templates are context engineering artifacts. A generated prompt has unknown
  accuracy until it is tested against real statements. Generating at runtime and using
  immediately creates a path for silently bad parses that pass review.
- The generation step adds significant latency to the first upload from a new platform.
- Prompt generation is non-deterministic — two runs of the same input may produce
  different templates.
- The "zero code change" benefit is illusory: someone still needs to review the generated
  template before trusting it. That review step (HITL for skills) adds a new workflow
  surface, new UI, and new backend endpoints — more total work than writing the template
  manually and committing it.

## Adding a New Platform

When a new platform is needed:
1. Create `agents/src/skills/platforms/<platform>.skill.ts` with a `SkillTemplate` object
2. Register it in `REGISTRY` in `registry.ts`
3. Test with a fixture statement file
4. Commit and deploy

This is one file + one line. The skill template is version-controlled, code-reviewed,
and tested before it reaches production.

## Consequences

**Good:**
- Zero operational complexity — no DB table, no cache invalidation, no HITL for skills
- Skill templates are version-controlled and code-reviewed
- `getSkill()` is O(1) and never fails in prod for a registered platform
- 400 with a clear supported-platforms list makes debugging trivial

**Accepted trade-offs:**
- Adding a new platform requires a code change and redeploy — acceptable for a
  developer-managed personal finance application
- The 400 error surface-level blocks the upload for unknown platforms; the user must
  contact the developer to add support
