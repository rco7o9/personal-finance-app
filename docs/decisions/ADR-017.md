# ADR-017 — Currency Normalisation: amount_inr on investment_transaction

## Status
Accepted

## Date
2026-04-25

## Context

The `investment_transaction` table records the `amount` column in the transaction's native
currency (INR or USD), determined by the asset's exchange. US equities on NYSE/NASDAQ are
purchased in USD; Indian equities, mutual funds, gold, and crypto are purchased in INR.

The `holding` table derives `avg_cost` and `total_invested` from these transactions. In Phase 2a,
this derivation used `amount` directly without currency conversion. As a result:

- A US equity holding bought for $100 would have `avg_cost = 100` (USD), while
  `current_price` is always in INR (returned by AssetPriceService).
- Computing `unrealisedGain = current_value - total_invested` compared INR against USD —
  producing numbers off by a factor of ~85–95.
- XIRR cash flows would mix USD outflows with an INR terminal value, producing nonsensical rates.

The problem was latent in Phase 2a (P&L was displayed but not validated). It became blocking
for Phase 2b XIRR, where all cash flows must be in a single currency.

## Decision

Add `amount_inr NUMERIC(18,4) NOT NULL` to `investment_transaction`:

- **INR transactions:** `amount_inr = amount` (1:1, no conversion needed)
- **USD transactions:** `amount_inr = amount × historical_USD_INR_rate` where the rate
  is fetched from Frankfurter API (`api.frankfurter.dev/v1/{date}?from=USD&to=INR`) for
  the exact transaction date, not an approximation.

The `holding` table is rebuilt from `amount_inr` so that `avg_cost` and `total_invested`
are always INR-denominated regardless of the asset's native currency.

XIRR cash flows use `amount_inr` exclusively — all flows are in INR, matching the INR
terminal value (`holding.current_price × holding.quantity`).

### Why a column on investment_transaction, not a view or derived value

- Preserves the raw `amount` (original currency) for audit/debugging
- Makes `amount_inr` queryable and indexable without recomputing on every read
- XIRR queries join many transaction rows; a stored column avoids repeated conversion

### Why historical rates, not a fixed approximation

The USD/INR rate ranged from ~73 to ~87 over 2020–2024. A fixed approximation would
introduce significant error on older transactions. The Frankfurter API provides free
historical rates and returns the nearest business day rate when a weekend/holiday is queried.

### Why NOT store converted values in holding directly

The holding table is derived state, recomputed after every transaction confirm. Embedding
currency conversion in the holding recompute would couple the holding rebuild to an
external API call. Storing `amount_inr` on the ledger row keeps the conversion close to
the source of truth and makes the holding rebuild a pure in-DB aggregation.

## Implementation

Migration: `backend/migrations/005_fix_price_coverage.sql`
- Adds `amount_inr NUMERIC(18,4)` column (nullable initially)

Seed script: `backend/scripts/seed-amount-inr.ts`
- Fetches historical USD/INR rates from `api.frankfurter.dev/v1/{date}?from=USD&to=INR`
- Backfills `amount_inr` for all INR and USD transactions
- Sets `NOT NULL` constraint
- Truncates and rebuilds the `holding` table using `amount_inr`

Portfolio service: reads `it.amount_inr` for `total_invested` in `queryPositions()` and
for lot `cost` in `getAssetDetail()`. XIRR cash flows also use `amount_inr`.

## Consequences

**Good:**
- P&L figures (unrealised gain, absolute return %) are correct for all asset classes
- XIRR computation is unambiguous — all flows in INR
- Re-running the seed script is safe and idempotent (can be re-run if new USD transactions
  are added in the future)

**Bad / Accepted:**
- `current_price` values are lost on the first seed run (holding table is truncated).
  A price refresh is required after the seed to repopulate `current_price`.
- If a future USD transaction is added without running the seed script, `amount_inr`
  must be populated manually or the script must be re-run. This is acceptable for a
  personal tracker with infrequent transactions.
