# ADR-020 — Investment Baseline: Household-Level Monthly Planned Investment

## Status
Accepted

## Date
2026-05-03

## Context

The `portfolio_allocation_target` table stores target category percentages for a given
date range (e.g. 32% US Equity by 2027-03-31). Previously, the allocation view compared
current holdings against these targets using the live portfolio value as the denominator.

This was misleading: if the user plans to invest ₹A more by March 2027, a category that
looks "on track" today at 32% of ₹B today might actually need ₹C more to stay at 32%
of the expected ₹(A+B) total. The bar chart and rebalancing suggestions were silent about
this gap.

The fix requires knowing how much the user plans to invest each month between now and the
target end date. Two design questions arose:

**1. Per-person or household-level?**
Expenses are tracked per-person (who spent what). Investments are different — Arjun manages
the household investment portfolio even when transactions go through Priya's account.
The `holding` and `portfolio_allocation_target` tables are already household-wide. A
per-person `investment_baseline` would require summing across persons on every read with
no benefit, since no per-person investment reporting is needed.

**2. Total amount or per-category breakdown?**
A per-category breakdown (e.g. "₹40k Indian Equity, ₹20k MF this month") would enable
more precise rebalancing suggestions ("put all of next month's investment into US Equity").
However, the user invests opportunistically based on valuations, not on a fixed monthly
category schedule. A total-only approach is sufficient: compute the expected total at
end_date, then let the existing target percentages derive the required absolute ₹ values
per category. The gap between current value and target absolute value is already actionable.

## Decision

Add a single `investment_baseline` table at household level with one row per month:

```sql
CREATE TABLE investment_baseline (
  id     SERIAL        PRIMARY KEY,
  month  DATE          NOT NULL UNIQUE,
  amount NUMERIC(18,4) NOT NULL
);
```

**Date convention:** The `month` column stores the **last day** of the month
(e.g. `2026-05-31`), intentionally deviating from the project-wide first-day-of-month
convention. This makes the range filter `month > CURRENT_DATE AND month <= end_date`
work correctly: a future month (e.g. May 31) is always `> today` until the last day
has passed, at which point the month is considered fully elapsed.

**Portfolio service integration:**

```
expectedTotal       = SUM(holding.current_value) + SUM(investment_baseline.amount
                          WHERE month > today AND month <= active target end_date)

percentage          = category.current_value / expectedTotal × 100
targetAbsoluteValue = target_pct / 100 × expectedTotal
delta               = percentage − target_pct
rupeesGap           = targetAbsoluteValue − current_value
```

The allocation bars, target markers, and rebalancing suggestions all use `expectedTotal`
as the reference point rather than today's live value.

**Known limitation:** `queryPlannedInvestments()` currently only sums future rows
(`month > today`). Past months in the target period where investment actually occurred
are not accounted for. This will be corrected when actual month-by-month investment
tracking is added — at that point, past months will use actual `investment_transaction`
amounts and only future months will use the baseline.

## Alternatives Considered

### Per-person investment baseline
Rejected. Investments are household-managed regardless of which account they go through.
Per-person breakdown adds join complexity with no reporting benefit.

### Per-category monthly allocation
Rejected. User invests opportunistically, not on a fixed per-category schedule. The total
is sufficient to compute expected absolute targets; the category split is a separate decision
the user makes at investment time. Adding category breakdown would require maintaining a
schedule that the user would not realistically keep up to date.

### First-day-of-month date storage (project convention)
Rejected for this table. The range filter `month > CURRENT_DATE` works correctly with
last-day dates: May 31 > May 3 (still upcoming), and once May 31 passes, the month is
fully elapsed. With first-day dates (May 1 < May 3), May would be incorrectly excluded
for most of the month.

## Consequences

**Good:**
- Allocation bars and rebalancing suggestions now reflect where the user needs to be
  by end_date given planned future investments, not just current snapshot
- `targetAbsoluteValue` per category gives a concrete ₹ target ("₹N in US Equity
  by Mar 2027") that is directly actionable
- `rupeesGap` in rebalancing suggestions makes underweight/overweight quantitative
- Table is minimal (3 columns) and easy to maintain

**Accepted trade-offs:**
- Last-day-of-month convention is a deliberate deviation from the project standard;
  documented here and in migration comment
- Past months in the target period contribute 0 to `plannedInvestments` until actual
  tracking is built (tracked as tech debt in phase note and memory)
- No currency column — INR assumed; acceptable for a household INR portfolio
