# ADR-026 — Expense Transfer Classification, Confidence-Gated Auto-Approval, and Per-Row Cardholder Attribution

## Status
Accepted

## Date
2026-08-01

## Context

Two gaps existed in the expense side of the Phase 3b ingestion pipeline once
credit card statement ingestion was added:

1. **Double-counting risk.** A bank statement's credit card bill payment line and
   the credit card statement's itemized purchases represent the same spend twice
   if both are inserted as expenses. The same is true of a transfer between the
   two household members (Arjun and Priya) and of a SIP/investment debit that
   is already captured by the investment ingestion pipeline. The schema already
   had `expense.transfer_type` (enum `investment_platform` / `household_member` /
   `own_account`, added in migration 002) for exactly this purpose, but
   `statements.service.ts` simply dropped any row Gemini tagged
   `internal_transfer` — the column was never populated.

2. **Review doesn't scale.** Every parsed expense row landed in manual review
   (`status = 'pending'`) regardless of how confident the extraction was. That's
   fine for investment statements (tens of rows/month, high stakes per row) but
   not for bank/credit-card statements (100+ rows/month).

3. **Shared credit card statement.** HDFC issues one PDF per account covering
   both the primary cardholder (Arjun) and the add-on cardholder (Priya).
   `person_id` on `expense` is `NOT NULL`, and the existing upload flow assumed
   one upload = one person (`metadata.personId`, selected once per upload). That
   assumption breaks for a statement containing both people's transactions.

## Decision

**1. Store `internal_transfer` rows instead of dropping them.**
`uploadStatement()` now keeps rows Gemini tags `rowType: "internal_transfer"` for
expense-type uploads (`income`, `investment`, and `ignore` rows continue to be
dropped, unchanged). `insertExpenseTransactions()` inserts them under a dedicated
`"Transfer"` expense category with `transfer_type` set to Gemini's classification.
Reports that compute total spend must filter `WHERE transfer_type IS NULL` — no
such report exists yet, so this is a forward-looking constraint, not a code
change made here.

Gemini classifies each transfer as one of three types via a `transferType` field
(required when `rowType` is `internal_transfer`):
- `own_account` — payment toward a credit card bill, EMI, or another account the
  same person owns (the credit card's own statement already itemizes this spend)
- `household_member` — the counterparty is the other household member, matched
  by name appearing in the transaction narration
- `investment_platform` — a SIP/broker debit already captured by the investment
  ingestion pipeline

**2. Auto-approve expense rows above a confidence threshold, gated on
statement-level verification.**
A row is inserted with `status = 'confirmed'` directly — skipping manual review —
when `confidence >= 0.85` **and** the statement's balance-check
`verificationStatus !== 'failed'`. The verification gate applies uniformly to
every row from that statement, regardless of individual row confidence: a
failed arithmetic check means something about the whole parse is untrustworthy,
and a confident-looking row from a bad parse is not evidence the row itself is
correct. This only applies to expense ingestion — investment rows always require
manual confirmation (`autoApproved: 0` always), since investment volume is low
and the stakes per row are high.

The threshold (0.85) matches the "low confidence" cutoff already used in the
investment review UI, so the same number means the same thing across both flows.

This required fixing a latent bug: the HDFC/ICICI bank statement Gemini prompts
hardcoded `confidence: 0.85` as a literal instruction, so every row got an
identical score. Auto-approval needs real per-row variance to be meaningful —
the prompts now include a calibration rubric (0.95–1.0 clear and unambiguous,
0.70–0.94 recognizable with some ambiguity, below 0.70 genuinely uncertain) with
high- and low-confidence few-shot anchors.

**3. Resolve person attribution per transaction row, not per upload.**
`ParsedTransaction` gains an optional `cardHolderName` field. For the
`hdfc-credit-card` skill, Gemini extracts the cardholder name printed against
each transaction/section. The backend resolves it to a `person_id` via a
case-insensitive substring match against `person.name`
(`resolvePersonId()` in `statements.service.ts`), falling back to
`metadata.personId` (the person selected in the upload UI) when the name is
absent or matches nobody. Bank statements (`hdfc-bank`, `icici-bank`) continue
using `metadata.personId` directly for every row — one bank statement PDF is
always one account belonging to one person.

Because a single upload can now resolve to either household member's
`person_id`, the expense dedup check was widened from "last 4 months for this
person" to "last 4 months for anyone in this person's household" (joined via
`person.home_id`), keyed on `(person_id, date, amount, description)` instead of
just `(date, amount, description)`.

## Why Not Drop Transfer Rows (status quo)

Keeps the change smaller, but silently discards the money trail — there would be
no record anywhere that a credit card bill was paid or that money moved between
household members. Given the household explicitly wants reconciliation
visibility ("don't double count, but don't lose the transaction either"), and the
schema already had a column built for exactly this, storing-and-tagging was the
only option that didn't waste existing design work.

## Why Not a Per-Upload Cardholder Selector

Splitting a single HDFC CC statement PDF into two uploads (one per cardholder)
isn't practical — the file is one PDF with both cardholders' transactions
interleaved by section, not two separate documents. A dropdown asking "whose
transactions are in this file?" doesn't work when the answer is "both." Per-row
extraction is the only approach that matches the actual structure of the source
document, and costs nothing extra since Gemini is already reading the statement
visually (same rationale as `source_text` extraction in ADR-023).

## Why Not Auto-Approve Everything Above Threshold Without the Verification Gate

Considered gating auto-approval purely on row-level confidence. Rejected: a
statement whose balance doesn't reconcile might still produce individually
confident-looking rows from Gemini (e.g. a systematic misread of one column that
doesn't affect how "sure" the model feels about any single row). Requiring the
statement-level check to also pass means a bad parse forces full manual review
even when no individual row raises a flag on its own.

## Consequences

**Good:**
- No more silent double-counting between a bank statement's CC payment and the
  CC statement's itemized purchases, or between the two household members'
  transfers
- Expense review queue only surfaces rows that actually need a human decision —
  scales to high-volume statements
- Confidence scores are now real signals instead of a hardcoded constant
- Shared credit card statement correctly attributes spend to the person who
  actually made it, not just whoever happened to click upload

**Accepted trade-offs:**
- `resolvePersonId()` does a substring `ILIKE` match on `person.name` — works for
  a two-person household with distinct first names; would need a more precise
  matching strategy (exact ID mapping, not name pattern matching) if the
  household grows or names collide
- The household-wide dedup query is now slightly more expensive (joins through
  `person.home_id` instead of a single `WHERE person_id = $1`) — negligible at
  current data volume
- `transfer_type IS NULL` is a filter every future expense report must remember
  to apply; no report exists yet to enforce this in code, only in this ADR

## Addendum — findings from a real HDFC Credit Card statement (2026-08-01)

Before this feature shipped, it was run against a real 5-page, 111-transaction
HDFC Credit Card statement (both cardholders present) as a verification loop.
That surfaced four additional bugs, all fixed in the same session:

**1. No `maxOutputTokens` set.** A statement with 100+ transactions, each
requiring a verbatim `source_text` field, produces enough output that the
default budget was a live risk. Set explicitly in `gemini.parser.ts`.

**2. `responseSchema` produces malformed JSON for this model on this shape.**
Constraining `gemini-3-flash-preview` with an API-level `responseSchema`
consistently broke partway through the `transactions` array on the real
statement (JSON parse failure at a consistent byte offset, reproduced twice).
The identical prompt *without* `responseSchema` returned clean, valid JSON
matching the intended shape, on a call that was also faster. `responseSchema`
was removed; the system prompt already enumerates every field, type, and enum
exhaustively, so schema enforcement was redundant with the prompt and actively
harmful for this model. If a future model/SDK version reintroduces this as a
non-issue, reconsider — but don't re-add it without testing against a real
multi-hundred-transaction file first.

**3. No request timeout.** The Google Generative AI SDK has no default
timeout; a stalled call would hang the entire synchronous
backend→agent→frontend chain (ADR-024) indefinitely. Added an explicit
150s→280s timeout (`REQUEST_TIMEOUT_MS` in `gemini.parser.ts`) — tuned upward
after 150s proved too tight for a genuinely-busy real statement's generation
time, converting a working-but-slow call into a false timeout failure.

**4. Credit card balance verification used the wrong sign.** The existing
`verify()` formula (`opening + credits − debits ≈ closing`) is correct for a
deposit/savings account, where a credit is money coming in. A credit card
balance is a liability: a purchase (debit) increases what's owed, and a
payment (credit) decreases it — the mirrored sign. Applying the deposit-account
formula to the real statement (opening ₹O, closing ₹C) computed
a value off by roughly 2× the debits — while the correct liability-mode formula
(`opening + debits − credits`) landed on the printed closing balance, within the ₹1 tolerance.
Added `balanceCheck: "opening_closing_liability"` as a new `SkillTemplate`
option; `hdfc-credit-card` uses it, bank statements keep the original
`"opening_closing"` mode.

**5. A fully empty Gemini response silently "passed" verification.** When
`parsedTransactions` is `[]` and both balances are `null`, the prior code
defaulted both to `0` before calling `verify()`, and `0 ≈ 0` trivially passed
— reporting a statement as successfully verified when nothing was actually
extracted. `verifierNode` now treats "zero transactions and no balances" as an
explicit failure that goes through the normal retry-then-fail path instead of
a false pass. Covered by a regression test in `graph.spec.ts`.

None of these would have been caught by synthetic fixtures or mocked Gemini
responses — they only appeared against a real, messy, multi-cardholder
statement with well over a hundred transactions. Confirms the value of running
a real-file verification loop before considering statement-ingestion changes
done, not just unit tests against hand-written fixtures.
