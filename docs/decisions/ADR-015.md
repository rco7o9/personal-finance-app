# ADR-015 — Portfolio is Household-Wide; Prices Served from Cached Holding Table with Explicit Refresh

## Status
Accepted

## Date
2026-04-25

## Context

Two design decisions from Phase 2a were revisited before Phase 2b implementation:

**1. Per-person vs household portfolio**
The original portfolio endpoints accepted a `personId` query parameter and filtered
`investment_transaction` by person. However, the portfolio represents the combined household
position — both Arjun and Priya invest together with shared goals and a shared allocation
target. Showing a filtered per-person portfolio is misleading for rebalancing decisions,
XIRR, and allocation reporting. `personId` remains meaningful for Phase 3+ expense and
investment ingestion flows, but not for portfolio state.

**2. Live price fetching on every page load (ADR-007)**
The Phase 2a implementation called live external APIs (Indian Stock Market API, Finnhub,
mfapi.in, CoinGecko, GoldAPI) on every `GET /portfolio/summary` request. This caused:
- 3–8 second page load latency (multiple sequential API round-trips)
- Rate limit pressure on free-tier APIs during normal browsing
- Risk of page failure when any upstream API is down

For a personal finance tracker used by two people, real-time prices on every visit are
unnecessary. The `holding` table already stores `current_price` from the last explicit refresh.

## Decision

**Portfolio endpoints are household-wide (no personId filter):**
- `GET /portfolio/summary` — no `personId` parameter; returns aggregate household portfolio
- `GET /portfolio/assets` — no `personId` parameter; returns all assets held across the household
- `GET /portfolio/assets/:assetId` — no `personId` parameter; lots show all household transactions

`personId` continues to be used in Phase 3+ for statement ingestion, expense attribution,
and income tracking.

**Portfolio pages use `holding.current_price` from the database (not live fetches):**
- `GET /portfolio/summary` reads `holding.current_price` directly — zero external API calls
- Portfolio loads immediately without external dependencies
- The frontend exposes a "Refresh Prices" CTA that calls `POST /portfolio/holdings/refresh`
- The refresh endpoint adds inter-request delays (≥500ms between API batch chunks) to
  avoid rate limiting on free-tier APIs

**Refresh endpoint rate-limiting behaviour:**
- Indian stocks (Indian Stock Market API): sequential chunks of 10, 500ms sleep between chunks
- Other sources (Finnhub, mfapi.in, CoinGecko, GoldAPI): parallel, unchanged

## Supersedes

ADR-007 (Portfolio values computed at runtime via live price fetching). The `holding` table
still has no independent price snapshot history — it stores only the most recently refreshed
price, not a time series.

## Alternatives Considered

1. **Keep live fetch but add a short cache (e.g. 5 min TTL in-memory)** — Already implemented
   as ADR-009. But cache is cold on every server restart and doesn't survive container restarts.
   Rejected: the holding table is a more durable cache with no additional infrastructure.

2. **Keep per-person portfolio, add a household aggregate endpoint** — Adds complexity with
   no benefit; household aggregate is the primary view for rebalancing decisions.

3. **Refresh in background on page load, show stale while revalidating** — Would require
   a background job or WebSocket push. Over-engineered for a personal tool.

## Consequences

**Good:**
- Portfolio page loads instantly (no external API calls in the critical path)
- No rate limit risk during normal browsing
- Page never fails due to upstream API outages
- Clear UX: user explicitly triggers a refresh and sees a spinner during the wait

**Bad / Accepted:**
- Prices can be stale (days old) if the user never refreshes — acceptable for a personal tracker
- `holding.current_price` is NULL for any asset that has never been refreshed or whose API
  returns no data; these show as "—" in the UI until fixed (see ADR-016 for coverage gaps)
