# ADR-022 — LangGraph Functional API for Workflow Orchestration

## Status
Accepted

## Date
2026-05-16

## Context

The statement parsing workflow has a known, predetermined sequence:

```
parse → verify → [retry with error context if failed, max 3] → return
```

Only the parse step is LLM-driven (for Gemini-based platforms). The verify step is a pure
arithmetic function. The retry decision is a conditional edge on verification outcome and
attempt count — deterministic, not LLM-driven.

Three orchestration options were evaluated:

1. **LangChain `createAgent()` with progressive tool disclosure**
2. **LangGraph Functional API**
3. **Plain async functions with manual retry loop**

LangChain v1's `createAgent()` is built on top of LangGraph and exposes a ReAct agent
that calls tools in a loop until the model produces a final answer. Tools are exposed
via middleware with state-based filtering (progressive disclosure).

## Decision

Use **LangGraph Functional API** (`@langchain/langgraph`) for the outer workflow.
Use Gemini structured output directly inside the `parse_node` — not a ReAct agent loop.

The graph has three nodes and one conditional edge:

```
parse_node  →  verify_node  →  return_node
                    ↑               ↑
              [fail, attempts < 3]  [pass or attempts = 3]
```

State flows through nodes as a typed `AgentState` object. The conditional edge from
`verify_node` reads `state.verificationStatus` and `state.attempts` — pure determinism.

## Why not createAgent() with progressive tool disclosure

`createAgent()` is the right abstraction when the LLM needs to decide which tools to
call and in what order — a research agent, a customer support bot, an open-ended coding
assistant. The statement parsing workflow does not have this property:

- The sequence is always parse → verify → (retry or return). The LLM does not decide
  whether to verify after parsing — it always happens.
- The retry decision is deterministic (arithmetic check failed + attempts < 3), not
  something an LLM should reason about.
- Expressing "go back to the parse step with modified context" inside a ReAct tool loop
  requires fighting the framework — the loop is designed to call tools forward, not
  revisit prior steps with updated state.
- Every invocation would pay for an LLM reasoning step to "decide" to call the parse
  tool — adding latency and token cost for a decision that is already made.

Progressive tool disclosure via middleware (filtering tools per platform) was also
evaluated. Since platform is known from metadata and routing is deterministic, disclosure
adds no value — the agent would always see exactly one parse tool and call it.

## Why not plain async functions

Manual retry logic (while loop + try/catch) works but has no typed state, no graph
visualization, and is harder to extend (adding a second conditional path requires
restructuring imperative code). LangGraph's Functional API gives these for free.

## Consequences

**Good:**
- Typed `AgentState` makes the data flowing between nodes explicit and testable
- Conditional edges make the retry logic declarative and inspectable
- LangGraph's built-in tracing integrates with LangSmith when needed
- Deterministic platforms (CSV/XLSX) short-circuit `parse_node` without entering any LLM path

**Accepted trade-offs:**
- LangGraph is a dependency even for CSV-only parses that never touch an LLM
- The Functional API is newer and has less documentation than the Graph API — prefer
  Functional API for its lower boilerplate; fall back to StateGraph if subgraph
  composition is needed later
