# ADR-006: Docker Compose as the Sole Development Environment

## Status
Accepted

## Date
2026-04-19

## Context
The stack requires four services to run together: PostgreSQL, NestJS backend,
Next.js frontend, and CloudBeaver (DB GUI). Each session needs all four to be
up and consistent. The risk of "works on my machine" configuration drift grows
quickly when services are installed locally at different versions or with
different configs across sessions.

Additionally, the backend and frontend must be able to resolve each other by
hostname (the frontend container calls `http://backend:3001`), which requires
a shared network — something Docker Compose provides natively.

## Decision
Docker Compose is the single source of truth for the development environment.
All four services are defined in `docker-compose.yml` at the repo root.
Development always starts with `docker compose up`.

No locally-installed PostgreSQL is required or expected. The `cloudbeaver`
service provides a web-based DB GUI at `:8978`, replacing the need for a
local Postgres client.

## Alternatives Considered

### Local installs (Homebrew postgres, node directly)
- Pros: No Docker overhead, faster startup, simpler mental model for a solo
  developer, easier to run `psql` directly.
- Cons: PostgreSQL version must be managed manually. Data directory, port
  config, and pg_hba.conf live in unpredictable locations depending on
  install method. No built-in inter-service networking (backend calling
  postgres by hostname). Easy to forget to start postgres before running
  migrate commands.
- Rejected: The Docker-internal hostname requirement (`http://backend:3001`,
  `@postgres:5432`) means Docker Compose is needed regardless for the
  inter-service network. Running postgres locally would mean maintaining two
  connection strings permanently with no benefit.

### Neon serverless Postgres for development
- Pros: No local Postgres at all, zero startup time, accessible from anywhere,
  branching feature useful for schema experiments.
- Cons: Requires internet connectivity for all development. pgtyped codegen
  connects to the DB — a slow or unavailable cloud DB blocks type regeneration.
  Adds a paid external dependency. Data lives outside the local machine.
- Rejected: Local-first is preferable for a personal finance app. Sensitive
  financial data should not transit to a third-party cloud service during
  development.

### Devcontainers (VS Code)
- Pros: Reproducible environment including editor extensions, locks even Node
  version and system tools.
- Cons: Ties the development workflow to VS Code specifically. Adds a layer of
  complexity (devcontainer.json, rebuild cycles) on top of Docker Compose,
  which we need anyway. Claude Code sessions run outside the devcontainer.
- Rejected: Docker Compose alone achieves the consistency goal without the
  editor lock-in.

### Turso / SQLite for local development
- Pros: Zero setup, embedded, instant startup, no Docker needed for the DB.
- Cons: Different SQL dialect from PostgreSQL (no `NUMERIC(18,4)`, no custom
  enums, limited full-text search). pgtyped requires a real PostgreSQL
  connection for type introspection. Would require dialect-switching between
  dev and any future hosted environment.
- Rejected: Schema and type compatibility between dev and prod is non-negotiable.
  SQLite cannot host the PostgreSQL-specific types this schema relies on.

## Consequences
- `docker compose up` is always the first command of any development session.
  All other commands (migrate, codegen, dev servers) depend on the containers
  being up.
- The DATABASE_URL footgun: migrations run from the host Mac use `localhost:5432`;
  the backend container uses `postgres:5432` (Docker service name). These are
  two different valid values for the same logical variable. See phase note for
  details.
- CloudBeaver at `:8978` provides a GUI DB explorer. No local `psql` or
  TablePlus/Postico required, though they work fine if pointed at `localhost:5432`.
- Docker Desktop must be running before development begins. On Mac, Docker Desktop
  startup adds ~10–20 seconds to the first session.
- Container logs are the primary debugging surface: `docker compose logs -f backend`.
