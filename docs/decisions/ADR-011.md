# ADR-011: Internal Transfer Detection via transfer_type on expense

## Status
Accepted

## Date
2026-04-24

## Context
When a bank statement (savings account or credit card) is parsed, it will contain
transfers that are not real expenses:

1. Transfers to investment platforms (Zerodha, INDMoney, PayTM Money) — money leaving
   the bank to be invested. The actual investment record arrives later via a separate
   investment statement from the platform.
2. Transfers between household members (Arjun → Priya or vice versa) — internal
   redistribution of household funds.
3. Transfers between own accounts (e.g. savings to a fixed deposit account).

These must be excluded from expense reports but should still be surfaced in HITL review
with a distinct UI treatment — the user should confirm them as transfers, not manually
hunt for and exclude them.

## Decision
Add a nullable `transfer_type expense_transfer_type` column to the `expense` table.

```sql
CREATE TYPE expense_transfer_type AS ENUM (
  'investment_platform',
  'household_member',
  'own_account'
);
ALTER TABLE expense ADD COLUMN transfer_type expense_transfer_type;
```

### Semantics
- `transfer_type IS NULL` — regular expense; appears in all expense reports
- `transfer_type IS NOT NULL` — internal transfer; excluded from expense reports

### HITL flow
During PDF parsing the AI classifier sets `transfer_type` when it detects a transfer
(by matching description against known `financial_institution` names and person names).
The row is inserted with `status = 'pending'`.

In the HITL review UI, rows with `transfer_type IS NOT NULL` are shown in a separate
"Internal Transfers" section with a "Confirm as transfer" action rather than the standard
confirm/edit/exclude options. Confirming sets `status = 'excluded'`.

If the classifier misidentifies a real expense as a transfer, the user can override:
clearing `transfer_type` routes the row back to the standard HITL review flow.

### Reporting query
Expense reports continue to filter `WHERE status = 'confirmed'`. Since confirmed transfers
have `status = 'excluded'`, no additional filter is needed. The `transfer_type` column
provides auditability — "show all investment platform transfers this month" — without
changing any existing report queries.

## Alternatives Considered

### Special expense_category for transfers
Considered: Use a built-in "Internal Transfer" expense category. Rejected: Categories are
user-visible labels for spending classification. Transfers are a fundamentally different
concept and should not pollute the category taxonomy. A dedicated column is cleaner.

### Separate `transfer` table
Considered: Route detected transfers to a separate table entirely. Rejected: Over-engineered
for Phase 3. The `expense` table already has the right structure (person, amount, date,
description, status). A column flag is sufficient.

## Consequences
- AI classifier must be prompted to detect and set `transfer_type` when parsing bank PDFs
- HITL UI (Phase 3) needs a distinct "Internal Transfers" section in the review flow
- Expense reports are unaffected — existing `WHERE status = 'confirmed'` filter is sufficient
- `transfer_type` enables future reconciliation: match `investment_platform` transfers in
  `expense` against `investment_transaction` rows from the same platform in the same month
