# ADR-001: Monorepo with Two Independent Apps (NestJS + Next.js)

## Status
Accepted

## Date
2026-04-19

## Context
Personal family finance tracker for two users (Arjun & Priya). The app needs a
UI layer and a data/business-logic layer. The core requirement was that all data
access, validation, and business rules live in one place — not scattered across
frontend server actions or API routes. The app is served via Docker Compose and
is not expected to be public-facing.

## Decision
Split into two independent npm projects sharing one Docker Compose environment:

- `backend/` — NestJS on port 3001. Owns all DB access, validation, and business
  logic. The only process that talks to PostgreSQL.
- `frontend/` — Next.js App Router on port 3000. Pure UI. Server components call
  NestJS via `fetch()` over the Docker internal network (`http://backend:3001`).
  Client components call `http://localhost:3001`.

No data fetching or business logic lives in the frontend. The separation is a hard
architectural rule, not a convention.

## Alternatives Considered

### Next.js fullstack only (API routes / Server Actions)
- Pros: Single codebase, no HTTP hop between frontend and backend, simpler Docker
  setup, faster iteration for a solo project.
- Cons: Business logic and DB access inevitably leak into route handlers and server
  actions. No clean boundary to enforce "no DB calls from UI code." Harder to add
  non-browser clients (CLI, mobile) later.
- Rejected: The blurred boundary was the main concern. Financial logic (XIRR
  calculations, status transitions, report queries) belongs in a dedicated service
  layer, not interleaved with rendering.

### T3 Stack (Next.js + tRPC + Prisma)
- Pros: Opinionated, well-documented, strong TypeScript end-to-end types via tRPC.
- Cons: Still a fullstack-in-one-repo pattern. Also bundles Prisma, which we
  explicitly decided against (see ADR-002). tRPC's RPC style is good for small
  apps but adds abstraction we don't need.
- Rejected: Conflicts with the no-ORM decision and doesn't provide the hard
  UI/logic separation we wanted.

### Single NestJS app with SSR
- Pros: One codebase, NestJS handles both API and server rendering.
- Cons: NestJS SSR (via `@nestjs/serve-static` or custom adapters) is not
  idiomatic and loses the Next.js App Router ergonomics. Template engines or
  manual SSR in NestJS are significantly worse DX than Next.js for a data-heavy
  dashboard.
- Rejected: The frontend benefits too much from Next.js's App Router, image
  optimization, and React ecosystem to justify NestJS SSR.

## Consequences
- Frontend server components must call NestJS over HTTP even though both run on
  the same Docker network — this is a deliberate boundary, not a performance
  concern.
- Two separate `package.json` files, lint configs, and build pipelines to maintain.
- All business rules have one canonical home: `backend/`. This is easy to enforce
  in code review.
- Adding a mobile app or CLI later requires only pointing at the existing NestJS
  API — no changes to backend needed.
- `API_URL` (Docker-internal) and `NEXT_PUBLIC_API_URL` (browser) must both be
  set correctly; they resolve to different hostnames.
