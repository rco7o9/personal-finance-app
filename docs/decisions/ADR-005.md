# ADR-005: Money as NUMERIC(18,4), Quantities as NUMERIC(18,8) — Never FLOAT

## Status
Accepted

## Date
2026-04-19

## Context
The app stores and calculates financial data: expense amounts in INR, investment
values, NAVs, unit quantities for mutual funds and crypto, and portfolio totals.
Financial arithmetic requires exact decimal representation. The choice of numeric
storage type has correctness implications that compound over time — a rounding
error in one row becomes a reporting error across thousands.

## Decision
All monetary amounts use `NUMERIC(18,4)` in PostgreSQL.
All quantities (units of securities, mutual fund units, crypto) use `NUMERIC(18,8)`.
`FLOAT` and `DOUBLE PRECISION` are banned from financial columns.

The precision choices:
- `(18,4)`: 14 digits before the decimal, 4 after. Handles values up to
  99,999,999,999,999.9999 — sufficient for any INR amount. 4 decimal places
  covers paise (2 places) with headroom for intermediate calculations.
- `(18,8)`: 8 decimal places for quantities where fractional precision matters
  (crypto units, mutual fund NAV-based unit calculations).

## Alternatives Considered

### FLOAT / DOUBLE PRECISION
- Pros: Native hardware arithmetic, slightly faster for bulk calculations,
  familiar to developers from general-purpose programming.
- Cons: Binary floating point cannot exactly represent most decimal fractions.
  `0.1 + 0.2 = 0.30000000000000004` is not a JavaScript quirk — it is
  fundamental to IEEE 754. PostgreSQL `FLOAT` has the same property.
  Rounding errors accumulate across aggregations. For a finance app tracking
  lakhs of rupees, even small per-row errors become significant in YTD totals.
- Rejected: Correctness is non-negotiable for financial data. FLOAT is
  inappropriate regardless of scale.

### Integer paise/paisa storage (smallest-unit integers)
- Pros: Exact integer arithmetic, no rounding ever, common pattern in fintech
  payment systems (Stripe stores amounts in paise).
- Cons: Every read and write requires a conversion factor (amount_paise / 100
  for display). The conversion must happen in the right place consistently —
  easy to forget and hard to audit. For investment quantities there is no
  natural "smallest unit" (crypto can have 8+ decimal places). Complicates
  pgtyped type generation and display formatting throughout the UI.
- Rejected: The conversion overhead and inconsistency risk outweigh the
  benefits for a personal app. NUMERIC gives exact precision without the
  ergonomic cost.

### DECIMAL with lower precision (e.g. NUMERIC(10,2))
- Pros: Simpler, matches "currency has 2 decimal places" intuition.
- Cons: 2 decimal places is insufficient for mutual fund NAVs (4 decimal
  places), crypto quantities (8 decimal places), and intermediate XIRR
  calculations. Would require different column types for different domains
  anyway.
- Rejected: Insufficient precision for the quantity use case; (18,4) and
  (18,8) are the right floor for this domain.

## Consequences
- `node-postgres` returns `NUMERIC` columns as JavaScript strings, not numbers.
  All arithmetic on monetary/quantity values in TypeScript must use a decimal
  library (`decimal.js` or `big.js`) — never cast to `parseFloat()` or native
  `number`.
- pgtyped will type these columns as `string` in generated interfaces. This is
  correct — do not override with `number`.
- Slightly more storage than `FLOAT` per row, negligible for a personal app.
- XIRR and portfolio calculations that involve many intermediate steps must
  keep values as `Decimal` objects throughout; only convert to string/number
  at the serialization boundary (API response).
