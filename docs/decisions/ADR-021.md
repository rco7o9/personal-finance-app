# ADR-021 — Agent Service as a Separate Process

## Status
Accepted

## Date
2026-05-16

## Context

Phase 3b requires an AI-powered statement parsing pipeline using LangChain/LangGraph,
Gemini, and platform-specific skill templates. The question was whether to build this
inside the existing NestJS backend (as a new module) or as a standalone service.

Arguments for embedding in NestJS:
- One fewer service to run and deploy
- Shared DB pool, shared config, no inter-service HTTP calls
- Simpler Docker Compose setup

Arguments for a separate process:
- LangGraph and LangChain bring a large dependency tree that has no place in the backend
- NestJS DI (`@Injectable`, `@Inject`) conflicts with LangGraph's own state management
  and functional graph pattern — you cannot naturally use LangGraph's entrypoint/task
  model inside a NestJS module lifecycle
- The agent is a pure parsing service (stateless, no DB access) — its dependencies and
  concerns are completely different from the NestJS backend's concerns
- Independent deployability: the parsing pipeline can be updated, restarted, or scaled
  without touching the backend
- The agent service can be tested in isolation with no NestJS test harness

## Decision

`agents/` is a standalone TypeScript/Express service at the repo root, parallel to
`backend/` and `frontend/`. It runs on port 3002 and is registered in Docker Compose.

The backend calls the agent via HTTP (`POST /parse`) and the agent returns parsed data.
The backend owns all DB writes. The agent has no DB credentials or schema knowledge.

## Alternatives Considered

### Embed as a NestJS module
Rejected. NestJS DI and LangGraph's functional/entrypoint graph model do not compose
cleanly. LangGraph state flows through typed graph nodes — wrapping this in NestJS
`@Injectable` services adds friction without benefit. Dependency bloat in the backend
package is also undesirable.

### Serverless function (Lambda / Cloud Run)
Rejected for now. A sync call from the backend requires the function to stay alive for
the duration of parsing (up to 120s for complex PDFs). Cold starts add latency.
Acceptable future migration path if the sync model changes.

## Consequences

**Good:**
- Clean separation of concerns — agent is a parsing service, backend is the application
- LangGraph and Gemini dependencies isolated to `agents/`
- Agent can be tested independently with fixture files and mocked Gemini responses
- NestJS stays lean

**Accepted trade-offs:**
- One additional service in Docker Compose (port 3002)
- Inter-service HTTP call adds ~10–20ms overhead on the happy path
- `AGENT_SERVICE_URL` and `INTERNAL_API_KEY` must be kept in sync between services
